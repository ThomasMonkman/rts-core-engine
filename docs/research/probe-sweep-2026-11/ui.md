# Interface / user-layer probe sweep: findings

Scope: behaviour of the user-side Lua VM's engine APIs in a live game (issue #11 territory).

## What ran

| Probe (`dev/probes/maps/`) | Real game | Ours | Covers |
|---|---|---|---|
| `probe_ui_units` | yes (3 runs; the last is complete, 0 interface errors) | yes | every `UserUnit` method on 16 named units at tick 120 and 225, unit globals, selection, unit settings and their latency, factory queue edits, same-frame select + order, `SimCallback`, a plane killed in flight |
| `probe_ui_controls` | yes (complete) | yes, at 4:3 and again at 16:9 (`--window-size 2560x1440`) | control tree (hidden / alpha / hit test / depth / destroy), text and font metrics, bitmaps, keyboard focus, input capture, edits, item lists, world camera, world view projection |
| `probe_ui_globals` | yes (second run, complete, 384 PROBE lines) | yes | session, time, pause, game speed, economy, armies, preferences, disk and path helpers, maths, strings, Lua library |
| `probe_ui_hover` | yes (second run, complete, 182 lines; one case disabled) | yes | `GetRolloverInfo`, `GetRightMouseButtonOrder`, buildable categories, orders from the interface, user threads, methods on a dead unit |

Logs: real `dev/probes/out/probe_ui_{units,controls,globals,hover}.faf.log` and the interface half of `probe_api_spot`; our logs are not kept. The real screen was 2560x1440 (16:9), ours 1024x768 unless stated.

Two probe-harness lessons that cost two real runs, worth knowing for any later probe: moho's Lua reports a C function's `type()` as `'cfunction'`, and moho's bindings count their arguments, so a call padded with trailing `nil`s raises the function's usage text.

## Differences

Severity: **A** used by FAF's interface Lua and wrong or raising; **B** used, small or situational effect; **C** unused by FAF or cosmetic. Confidence is in the real-game reading, not in the suggested cause.

### The known 0.81 camera item

At the same aspect ratio the projection agrees to three decimals: with `SnapTo(..., zoom 100)` both engines give `pixels per world unit x zoom / view width = 1.000`, the same `+20z` and `+20y` screen offsets, the same `UnProject` and the same `GetMaxZoom`. The earlier 4:3 run differed only by the aspect ratio. So a `SnapTo` zoom shows the same ground width in both; the 0.81 factor is more likely a comparison across aspect ratios or the `Reset` zoom (row 21, 0.79) than the camera maths.

## After the `--ui-lua` fix

`--ui-lua` code now goes through `lua_translation` (`ui::run_source`, the same path as the console's `ui_lua`; `5d05759`), and `^` is translated to XOR (`af857a4`, api L1). Ours was rerun for all four interface probes with that build against the real logs already in `dev/probes/out/`.

No numbered row 1-62 was an artefact of the untranslated path. The probes had been written to avoid `!=`, `arg`, bit operators and bare `for k in t`, so translating them changed no result on its own: the set of differing cases is identical before and after for all four probes (units 367, controls 89, globals 157, hover 55), and the only value changes are run-to-run timing (`GameTick` stamps, positions, a health value mid-build).

The language lines of `probe_ui_globals` do change, because the `^` cases now go through the XOR rewrite and match the real game: `lua tostring ints` (`2 ^ 53` = `55` in both, was `9007199254740992`) and `lua integer division results` (`3.50 8.00 2.00 4.00 -0.00` in both, was `1024 1.41 -4`).

Still real differences: every numbered row not marked fixed in the State column, and the other Lua-runtime lines (float32 `tostring`, `%.0f` / `%5.1f` rounding, 3-digit exponents, `tonumber('0x10')`, string arithmetic, `table.getn` / `setn` / `concat` / `insert` / `remove`, `gsub` replacement checks, library name lists, `unpack` holes, pcall error values and positions, `type()` = `cfunction`). `lua select/arg` still differs only in which name is reported missing (`select` in the real game, `arg` in ours: the function is not a vararg one, so the translator rightly leaves `arg` alone).
